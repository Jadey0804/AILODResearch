# AILOD Phase 8 正式结果分析（大白话版）

日期：2026-08-31  
正式代码提交：`7699bbffdbcca536758f243f84a73b466230d65d`  
构建：UE 5.4.4，Win64 Shipping，NullRHI  
正式数据：480 个准确性 Runs；90 个性能 Runs  

## 1. 一句话结论

Proposed 展现出清楚的规模收益。它在 2k 人口下承担了较高的固定宏观模拟成本，在 10k 人口下开始快于 Per-Agent，在 20k 人口下达到约 `3.94×` 的中位整场加速。它对宏观轨迹、政策效应、身份、住房和大部分资源状态的保真度明显高于 Simple。普通任务“是否仍在进行”的快照状态仍有约 `90.83%` 的中位不一致率，这是当前方法最重要的连续性限制。

## 2. 这批数据回答什么

研究问题可以用大白话写成：

> 当游戏需要保存大量居民的长期生活状态，同时只允许少量 NPC 使用完整 Actor 和微观逻辑时，Structured Macro Simulation 能否随着人口增长节省计算，并在居民重新变成详细 NPC 时保留足够连续的身份、资源、住房、行为和任务状态？

正式实验分成两部分：

- 准确性实验使用 200 人，因为 Oracle 需要逐个居民做详细参考模拟。4 个方法、4 个场景和 30 个配对 Seed 形成 480 个 Runs。
- 性能实验使用 2k、10k、20k 人口。Proposed、Simple、Per-Agent 在 StateImport 压力场景下各重复 10 次，共 90 个 Runs。

每个准确性比较都使用相同 Seed。每个性能速度比都使用相同人口和相同 Repeat 编号。这样可以减少输入差异对结果的干扰。

## 3. 统计口径

- 中位数表示一组运行排在中间的结果，受偶发慢运行影响较小。
- IQR 是中间 50% 结果所在的范围，用来描述波动。
- 95% CI 是均值的双侧 t 区间，用来描述当前样本对均值的估计范围。
- 准确性误差越小越好。Oracle 自身误差为 0。
- 性能加速比等于 `Per-Agent 整场 AI CPU / 当前方法整场 AI CPU`。大于 1 表示当前方法更快。
- 性能主指标是 Day -7 到 Day 60 的整场生产 AI CPU 总和。墙钟采样桶的 Mean/P95/P99 只描述桶形状，不回答整场模拟速度。
- 所有正式硬错误总数为 0。

本分析完整保留每个指标，没有把几十项误差压缩成一个未经预先冻结的“综合准确性分数”。

## 4. 性能发现

### 4.1 Proposed 与 Per-Agent

| 总人口 | Proposed 整场 AI CPU 中位数 | Per-Agent 中位数 | Proposed 配对加速比中位数 | 加速比 IQR | 加速比均值 95% CI |
|---:|---:|---:|---:|---:|---:|
| 2,000 | 4,528.251 ms | 638.952 ms | 0.140× | 0.135–0.142× | 0.134–0.143× |
| 10,000 | 4,826.293 ms | 6,252.639 ms | 1.295× | 1.253–1.363× | 1.251–1.350× |
| 20,000 | 4,813.502 ms | 19,008.582 ms | 3.944× | 3.653–4.144× | 3.710–4.107× |

结果显示：

- Proposed 在 2k 时的整场 AI CPU 约为 Per-Agent 的 7.1 倍。固定的宏观管线、批处理和一致性维护成本在小规模下占主导。
- Proposed 在 10k 时获得约 1.30× 中位加速。规模收益已经超过固定成本。
- Proposed 在 20k 时获得约 3.94× 中位加速，达到此前设定的 3× 工程目标。
- Proposed 的整场 AI CPU 在三档人口中保持在约 4.5–4.8 秒。Per-Agent 从约 0.64 秒增长到 6.25 秒，再增长到 19.01 秒。这组趋势直接支持“宏观模拟成本不会跟每个居民一起线性增长”的设计目标。

这里的“秒”来自 AI CPU 毫秒相加后的换算，表示本实验的生产模拟 CPU 成本。它不表示玩家等待时间、FPS 或有画面渲染性能。

### 4.2 Simple 的意义

| 总人口 | Simple 整场 AI CPU 中位数 | 相对 Per-Agent 加速比中位数 |
|---:|---:|---:|
| 2,000 | 35.883 ms | 17.728× |
| 10,000 | 35.991 ms | 173.964× |
| 20,000 | 35.716 ms | 532.509× |

Simple 只保留很粗的总量，所以速度非常快。后面的准确性结果显示，它同时产生了很大的宏观、行为和居民状态误差。Simple 提供了“最低计算成本”的参考端点，无法单独满足本项目的长期连续居民目标。

### 4.3 内存结果

| 总人口 | Proposed 进程峰值中位数 | Per-Agent | Simple |
|---:|---:|---:|---:|
| 2,000 | 235.725 MB | 175.336 MB | 173.596 MB |
| 10,000 | 235.348 MB | 192.275 MB | 175.197 MB |
| 20,000 | 238.797 MB | 223.904 MB | 180.789 MB |

Proposed 在三档测试中都使用了更高的进程峰值内存。20k 时差距缩小到约 14.9 MB，但数据仍不支持“Proposed 更省内存”的结论。该指标是整个 Shipping 进程的 Used Physical Memory，包含 UE 引擎、日志缓冲、容器和模拟状态。它无法分离某一种居民结构的独占内存。

|---|---:|---:|---:|
| None | 0.000322 | 0.781507 | 0.000000 |
| HarvestCap | 0.000322 | 0.775135 | 0.000000 |
| StateImport | 0.000322 | 0.785365 | 0.000000 |

Proposed 的行为比例非常接近 Oracle。Simple 的 TVD 大约为 0.78，说明它无法保持详细模拟中的行为结构。Per-Agent 在 200 人准确性规模下与 Oracle 相同。

负的 Proposed-Simple 差值表示 Proposed 更接近 Oracle。这四项配对区间都完整落在 0 以下，说明当前 30 个配对 Seed 中的改善方向稳定。

## 6. 跨 LOD 连续性

下面使用 StateImport 场景。每个 Run 有 60 个配对居民快照。

| 指标 | Proposed 中位数 | Simple | Per-Agent | Proposed-Simple 配对均值差 95% CI |
|---|---:|---:|---:|---:|
| PersistentID 不一致率 | 0.000000 | 0.000000 | 0.000000 | 0.000000 |
| HomeID 不一致率 | 0.000000 | 0.000000 | 0.000000 | 0.000000 |
| HomeState 不一致率 | 0.033333 | 0.166667 | 0.000000 | -0.145625 至 -0.114375 |
| Money 相对 MAE | 0.647857 | 1.829325 | 0.000000 | -1.244601 至 -1.086579 |
| InventoryWood 相对 MAE | 0.066667 | 0.491667 | 0.000000 | -0.449370 至 -0.403963 |
| CurrentGoal 不一致率 | 0.016667 | 0.033333 | 0.000000 | -0.029580 至 -0.007087 |
| FirstAction 不一致率 | 0.033333 | 0.033333 | 0.000000 | -0.020826 至 -0.001396 |
| TaskActiveStatus 不一致率 | 0.908333 | 0.091667 | 0.000000 | +0.739677 至 +0.822546 |

这些结果支持三个判断：

1. Proposed 完整保存了 ResidentID、HomeID、Kingdom 和 Profession 等静态身份关系。
2. Proposed 对房屋状态、金币、随身木材和当前目标的保真度明显高于 Simple，同时仍有可测量误差。Money 相对 MAE 的中位数约为 0.65，资源连续性仍有改进空间。
3. Proposed 的普通任务激活状态与 Oracle 大量错位，中位不一致率约为 90.83%。这个指标来自 60 个配对快照，方向稳定。它说明宏观调度和详细任务计时尚未在所有观察时刻对齐。

TaskRemainingHoursMAE 的中位数为 0。每个 StateImport Run 中，双方“目标相同且任务同时激活”的可比较样本中位数只有 4 个，范围为 1–13。承诺任务相关指标的分母中位数为 3 或 2，并且存在零分母 Run。这些指标只能作为小样本诊断，不能用于宣称任务计时已经完全连续。

EventID、ReservationID 和 TaskProgress Exact 属于内部表示诊断。Proposed 的 EventID Exact mismatch 为 1，反映宏观事件表示与 Oracle 的内部编号体系不同。玩家可见连续性结论使用 ResidentID、HomeID、资源、房屋、目标和动作指标。

## 7. 可信度和限制

### 7.1 可信度来源

- 570 个正式 Runs 全部由同一 Git 提交和 Shipping Game 产生。
- 每份 Manifest 都通过正式资格门，全部硬错误为 0。
- 30 个准确性 Seed 使用配对设计。
- 10 个性能重复使用相同 Repeat 编号配对 Per-Agent。
- 方法顺序由冻结的 OrderSeed 随机化。
- 原始 CSV、Schedule 和审计文件都有 SHA-256，可重新核对。
- 工作簿完整保留 21,720 行准确性汇总和 3,150 行性能汇总，并用公式生成差值和统计表。

### 7.2 研究限制

- Oracle 只在 200 人规模运行。大规模准确性依赖小规模参考结果和同一模型语义，当前数据没有提供 20k Oracle。
- 每个人口档只使用一个模拟 Seed，并做 10 次运行重复。它能测量运行时波动，无法覆盖大量不同社会初始状态。
- 性能使用 NullRHI。结论针对模拟 AI CPU，不包含真实角色渲染、动画、GPU 和完整游戏帧率。
- Proposed 在 2k 下更慢，说明该方法适合达到一定人口规模后的场景。
- 进程内存指标无法解释具体数据结构的分配成本。
- 任务激活状态不一致显示了 Structured Macro 与详细任务计时之间的剩余语义差距。
- 本分析同时检查很多指标。结果以完整效应量、方向和区间呈现，没有通过挑选少量 p 值制造显著性结论。

## 8. 项目贡献可以怎样写

本项目实现并验证了一条完整的 NPC Simulation LOD 管线：

1. 每个居民拥有稳定 ResidentID、住房、资源、事件和任务状态。
2. 玩家附近的居民使用 Active NPC Actor 和详细模拟。
3. 远处居民进入 Structured Macro Simulation，以 Cohort、Joint Cell 和 Batch Event 降低逐居民更新成本。
4. 居民在 LOD 切换时通过统一状态桥接恢复身份和玩家可见状态。
5. 小规模 Oracle 用来测量准确性，大规模 Per-Agent 用来测量扩展成本，Simple 用来展示最低成本和相应准确性代价。
6. 正式结果显示 Proposed 的计算收益随人口增长出现，在 20k 达到约 3.94× 中位加速；宏观准确性接近 Oracle；任务激活连续性仍是明确限制。

这个贡献可以概括为：项目提供了一个可运行、可测量、可审计的 NPC Simulation LOD 原型，并用正式数据展示了规模、宏观保真度和微观连续性之间的实际权衡。
