## 1. 本步只回答什么问题

6F 已证明性能测量链路可用，同时发现单次 20k 工程冒烟中 Proposed Macro 成本很高。6G-A 不优化代码，只回答：Proposed Macro 的时间主要花在什么边界，开启诊断是否会改变模拟结果。

为此，6G-A 把 Macro 路径拆成七段：

1. 居民扫描与 Cohort 分组；
2. Cohort 代表合成与规划；
3. 成员分配与候选构造；
4. 候选排序；
5. 竞争准备；
6. 竞争检查；
7. 动作提交。

本步没有更改 Cohort Key、代表规则、成员分配、竞争顺序、个人 CoreState、事件、账本、资源守恒或确定性规则。

## 2. Profile 的工程边界

- `bEnableMacroProfiling` 默认关闭，只有工程请求显式开启时才计时。
- 开关关闭时，Manifest 记录 `enable_macro_profiling=false`，且不产生 `macro_profile` 子对象。
- 开关开启时，累计值写入既有 `run_manifest.json` 的 `measurement_summary.macro_profile`；没有新增文件，也没有改动 `performance_1s.csv` 的冻结 Schema。
- Replay 从 Manifest 恢复该开关，但 Profile 时间和计数不进入领域 Digest。
- 七段计时是 Macro 总时间的子集；未归因部分包括 Cohort Key 排序等段间工作以及计时调用本身的开销。
- `ActionCommit` 是宽边界，包含动作复核、事件创建、Scheduler、按动作需要的 Reservation/Ledger、居民 CoreState 写回，以及竞争失败后的独立 Wait 提交。它尚未细分到具体容器或函数。
- 现有 Macro 计费会扣除 Active Micro 的规划时间，但共享的候选排序和提交仍留在 Macro；因此候选数与 `ActionCommit` 也包含 Proposed 当小时最多 50 个 Active Micro 候选。这与既有成本口径一致，在 2k—20k 中占比很小，但不应把该边界误写成“纯 Cohort 成员提交”。

## 4. 用大白话解释结果

Cohort 确实把“做决定”的次数压得很低：10k 和 20k 在整个 67 游戏日累计都只有 2,848 个非空分组需要代表规划。因此当前问题不是“群体想得太慢”。

问题在决定之后。系统仍然要把群体结论逐个落实到具体居民：为每个候选重新检查、创建个人事件、放进 Scheduler，必要时处理 Reservation/Ledger，再写回这个人的状态。20k 一共处理了约 403 万个候选，这个个人承诺边界占已归因时间的约 91%。

这也解释了当前架构的真实取舍：项目已经节省了个人决策计算，但为了保留身份、历史、事件和资源一致性，还没有节省个人提交成本。该成本不能靠删除个人状态来逃避，否则会破坏当前研究问题；后续只能在不改变语义的前提下优化提交实现。

## 7. 结论边界与下一确认门

6G-A 只证明在本次固定工程条件下，动作提交是 Proposed Macro 的最大候选瓶颈，并且 Profile 没有改变领域结果。它不能证明正式 Speedup，也不能证明事件容器、Scheduler、Ledger、字符串账户或其他某一个内部操作就是根因。

项目作者已于 2026-08-18 确认 6G-A 并授权本地封板提交。后续 6G-B 的范围仍须先完成规则审查；在选择具体修改前，应核对 `ActionCommit` 宽边界内部的事件创建、调度、资源事务和状态写回成本，不能因为先前猜测而优先改 Cohort Key 或缓存分组。

若 6G-B 只做现行 v1.6 内的无损优化，则必须使用独立分支并保持三档 Digest、硬错误、个人 CoreState、独立事件/承诺、资源规则和日志 Schema 不变。若规则审查决定采用聚合提交和动态解聚，则必须先用新的版本化规格明确覆盖这些 v1.6 边界，再另行确认实施；本次确认不等于已授权 6G-B 编码。
