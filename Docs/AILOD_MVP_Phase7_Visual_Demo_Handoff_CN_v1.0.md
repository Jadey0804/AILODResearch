## 1. 先用一句大白话说明项目现在到哪了

后台社会模拟已经搭好并经过工程验收：项目能够保存 100,000 个居民身份，用少量群体批量推进远处社会，只把最多 50 名玩家正在关注的居民恢复成详细个人；居民离开再回来时，姓名、身份、房屋、资源和正在进行的维修不会凭空丢失。

现在缺的不是再造一套 AI，而是给这套已经能运行的模拟接上地图、俯视相机、鼠标移动、NPC 模型、时间按钮和望远镜，让玩家能直观看到“远处按群体算、附近按个人算”的切换过程。

### 1.1 常用词的大白话解释

| 文档里的词 | 大白话意思 |
|---|---|
| Cohort | 当前情况相近、可以一次批量计算的一群远处居民 |
| Active Micro | 玩家正在近距离关注、系统为其恢复了完整个人状态的居民 |
| Lift / Restrict | 把居民从后台群体中拆出来成为详细个人 / 玩家离开后把他安全合回群体 |
| Actor | 地图上真正能看到、移动和播放动画的 UE 对象；它只是居民的“身体外壳” |
| 权威状态 | 最终说了算的那一份数据，其他 UI、Actor 或缓存只能读取它 |
| Digest | 用来检查同一输入是否得到同一模拟结果的一串摘要值 |
| Seed | 控制确定性人口和事件生成的一组数字；Seed 相同才有条件复现实验 |
| Run | 从初始化到结束的一次完整模拟 |
| NullRHI | 不真正渲染画面的工程运行方式，适合测后台模拟，但不能代表有画面时的帧率 |
| P95 | 100 次耗时从快到慢排列后，接近第 95 次的值，用来看偶发卡顿而不只看平均值 |

## 4. 项目研究的核心到底是什么

项目不是要让 100,000 个 UE 角色同时出现在屏幕上，也不是要制作完整的《冰汽时代》或《博德之门》。核心研究问题是：

> 能不能让大量远处居民以群体为单位低成本运行，同时保留稳定身份和玩家关心的个人连续性；当玩家靠近或用望远镜观察时，再把少量居民恢复成可信的详细 NPC，并测量这样做比所有居民逐个计算快多少、误差有多大。

几个容易说错的地方：

- `Oracle` 是 200 人的详细参考，不是绝对真实世界，也不要求 Proposed 与它逐人、逐小时完全相同；
- Proposed 的身份和紧凑房屋记录仍随总人口增长，不能声称内存完全不随人口增长；
- Proposed 的优势来自远处居民不逐人思考、不逐人创建事件和 Actor，而不是让所有居民“消失”；
- 主实验使用固定政策和固定激活轨迹；镜头与望远镜属于演示或额外实验，不能选择主实验样本；
- 地图、模型和动画只负责展示，不能成为资源、任务或身份的第二套真相。

## 5. 截止目前真正完成了什么

### 5.1 模拟基础

- 一个统一的游戏时间、事件队列、资源账本、预约、政策时间线和竞争入口；
- Oracle、Proposed、Per-Agent、Simple 四种方法共享相同的场景和动作含义；
- 人口、金币、木材、事件归属、重复付款和重复完成都有硬检查；
- 一次完整模拟从 Day -7 运行到 Day 60，共 1,608 个小时步；
- 实验器支持初始化、逐小时推进、结束、记录、回放、离线重建、固定乱序、重复轮次和断点续跑。

### 5.2 Proposed v1.9

- 所有居民永久拥有稳定 `ResidentID / PersistentID / HomeID / NameSeed / AppearanceSeed` 等身份；
- 远处社会由少量 Cohort 联合状态、批量资源请求和批量事件推进；
- 每小时不允许扫描全部居民，也不允许按总人口展开个人候选和个人事件；
- 任意居民都可以从后台群体中恢复成详细个人，再安全合回；
- 同时处于详细个人状态的居民硬上限仍是 50；
- 具体房屋会记住完好、等维修、维修中或已修好；
- 如果玩家观察到居民正在维修，离开后再回来，系统能接回对应维修任务和剩余时间；
- v1.9 的领域摘要版本为 `1.9-domain-v1`；模型工程资格已经开放。

### 5.3 实验和测量工具

- 生产模拟、检查工具、快照、观察记录和文件写入成本已经分开；
- 200 人可以比较 Oracle 与 Proposed 的个人误差；
- 2k、10k、20k 可以比较 Proposed、Simple 和 Per-Agent 的运行成本；
- Proposed 已进行 50k/100k 工程压力检查；
- 可以分别统计领域结果、逐步运行成本和各权威数据容器的内存；
- 普通 Development 工程运行不会因为模型被批准，就自动变成论文正式数据。

## 7. 作者已经明确想要的最终可视化

### 7.1 镜头与玩家

- 参考《博德之门》的斜俯视角；
- 相机平时可以跟随玩家移动；
- 相机也可以脱离玩家自由平移；
- 玩家主要用鼠标点击地面移动；
- UI 有暂停、1 倍、2 倍、4 倍等时间控制；
- 暂停模拟后，相机和 UI 仍然可以操作。

### 7.2 NPC 加载

- 屏幕上不生成全部逻辑居民；
- 相机附近或当前真正需要观察的居民才恢复为详细 NPC Actor；
- 远处允许显示少量绑定真实 ResidentID 的 Cohort 轻量代理；它不是完整 NPC Actor，也不能假装知道尚未恢复的精确个人行动；
- 望远镜持续观察代理后，才请求把同一 ResidentID Lift 为详细 Active NPC；
- 居民离开观察范围后，回收的是 Actor 和详细表现，不是居民身份和历史；
- 同时详细运行的真实居民总数始终不超过 50。

### 7.3 望远镜实验

- 玩家打开望远镜观察远处区域；
- 被望远镜明确看到并持续观察的中心居民，按固定、可重复的规则从代理提升为详细 NPC；
- 第一版保留一个当前追踪居民；即使远处地图和 Actor 被卸载，也保存该 ResidentID 和独立空间连续性，玩家后来可以在合理街区/住宅/工作点找到同一个人；
- 例如第一次看到某居民砍柴，停止观察一段时间后再看，他的姓名、身份、工作、房屋和已建模任务不能出现明显穿帮；
- 望远镜选择和加载过程要能够记录与回放；
- 望远镜只用于演示或单独的额外实验，不混入正式固定激活轨迹。

## 8. 当前架构能不能支持这个目标

结论：**能支持，但还缺一层专门连接“后台模拟”和“地图 Actor”的桥。没有推翻 v1.9 的必要。**

已经具备的底座：

- 底层权威会话已经能按任意 ResidentID 恢复居民、合回居民、读取身份、读取 Active 状态和剩余任务时间；
- v1.9 已能保存稳定身份、房屋和维修任务连续性；
- Active 上限和迁移硬检查已经存在；
- 模拟能一小时一步推进，适合被可视化控制器按帧调度；
- 观察者已经被限制为只读，可以沿用“画面不能回写权威状态”的边界。

目前缺少的关键连接：

- 对外的 `FUnifiedSimulationSession` 目前只公开初始化、推进一小时、结束和读取时间，没有公开“把这一组居民设为当前观察对象”的接口；
- 现有 v1.9 运行时内部仍自动执行 Day 7/8、14/15、30/31、45/46 的固定激活轨迹；互动镜头不能和这套正式轨迹同时争抢 50 个名额；
- 居民身份没有地图坐标、所在街区、住宅位置、工作地点或稳定站位；
- 个人模拟状态只有钱、补助、木材、房屋和动作，没有连续路径、世界坐标或动画进度；
- UE 内容仍基本是 Third Person 模板，没有研究地图、俯视相机、专用 PlayerController、NPC Actor 池、Widget 或望远镜；
- 当前只发现一张 `ThirdPersonMap`，没有可识别的专用 UI/望远镜资源，也没有在现有内容中确认导航网格配置；
- 当前模块依赖尚未显式加入 UI、AI 或导航相关模块；需要到实际实现步骤再按最小需要增加。

这些都是 Phase 7 应补的展示层和接线，不代表模拟核心失败。

## 9. Phase 7 开始前必须先冻结的规则

以下推荐方案已经在 2026-08-23 的 Phase 7-0 讨论中由作者确认，并写入 `AILOD_MVP_Prototype_Phase_Acceptance_Spec_CN_v2.0.md`。本交接仍只做导航，发生冲突时以 v2.0 展示协议为准。

### 9.1 正式模式与互动模式分开

- 正式实验模式：只执行冻结的固定激活轨迹，不看镜头，也不开互动望远镜；
- 互动演示模式：只根据相机、玩家和望远镜选择居民，不再自动执行正式固定轨迹；
- 两种模式互斥，不能同时占用 Active 名额；
- 互动记录永远不能冒充正式 480/90 Runs。

### 9.2 Actor 与真实居民的关系

第一版坚持最容易解释的完整 Actor 规则：

> 一个可见、可检查的 NPC Actor，必须一对一绑定一个真实的 Active Micro ResidentID。

Actor 可以放回对象池重复利用，但未绑定的隐藏 Actor 不算居民。远处 Cohort 轻量代理也必须绑定真实 ResidentID，但它不是完整 Actor，不显示尚未恢复的精确领域行为。禁止没有真实身份的假人群。

### 9.3 50 人名额怎样分

推荐初始预算：

- 普通相机附近保留约 30—40 人；
- 望远镜优先锁定中心目标，并最多带 4 名上下文居民；
- 剩余名额用于切换缓冲和重要任务；
- 总数无论如何不能超过 50；
- 进入范围和退出范围使用不同距离，避免 NPC 在边缘不断出现、消失。

当名额不够时，应提前计算整组替换结果，再一次性提交。不能先卸下一半、发现失败后留下半套状态。

### 9.4 谁应该优先加载

建议按以下顺序选择，人数相同时用 ResidentID 作为稳定的最后排序：

1. 望远镜中心目标；
2. 玩家身边居民；
3. 画面中心居民；
4. 正在做维修等重要承诺任务的居民；
5. 以前观察过的居民；
6. 观察范围边缘的其他居民。

### 9.5 地图位置不能每帧扫描 100k 人

- 初始化时为 ResidentID / HomeID 确定性分配街区、住宅展示点、职业工作区和稳定站位；
- 使用空间格子或等价索引，只查询镜头附近格子；
- 相机移动时不能每帧遍历 100,000 个身份再算距离；
- 必须记录每次空间查询看了多少候选；
- 从 20k 增长到 100k 时，单次镜头查询工作量不应跟着接近 5 倍增长。

### 9.6 动画不能变成第二套 AI

- 模拟只告诉表现层“这个居民在做 Work / ChopWood / Repair / Wait 等动作、任务何时结束”；
- 表现层把动作映射到固定工作点、森林、市场、住宅和对应动画；
- NPC 的走路路径和当前动画帧可以是表现数据，但不能自行决定工资、资源、维修结果或下一项研究动作；
- 第一次回来时至少保证“同一个人、合理地点、合理动作、合理进度”，不承诺恢复到离开前完全相同的脚步或动画帧。

### 9.7 可视化专用运行档位

现有 Accuracy 每小时做完整研究记录，对大人口实时演示太重；Performance 又不提供 UI 需要的居民快照。建议新增 Demo 档位：

- 使用和 v1.9 相同的生产模拟规则；
- 只输出王国摘要和最多 50 名 Active 居民的只读展示快照；
- 使用较轻或定期执行的完整检查；
- 永远标记为不能用于正式实验；
- UI 显隐、模型开关等“不发送观察请求”的纯表现操作不能改变领域摘要；相机若因此选择了新的 Active 居民，则属于互动命令，必须记录并与正式实验分开。

### 9.8 时间加速按帧分摊

- 暂停只停止模拟时钟，不要粗暴停止整个 UE 世界；
- 1x / 2x / 4x 需要先定义“每真实秒推进多少游戏小时”；
- 不要为了追赶倍率在同一帧连续塞入大量 `StepHour`；
- 把待推进的小时分散到多帧，并设置每帧最多允许的模拟预算；
- 第一版先在游戏线程协调，不要在尚未明确线程安全前把模拟随意搬到后台线程。

### 9.9 固定地图、有限 PCG 和共同布局来源

- 作者只手工画少量道路、圈住宅/森林区域并放林场、采购点等重要地标；
- PCG 使用固定 Seed 在编辑器中批量生成房屋和树木，并把结果保存下来；第一版不在运行时重新规划王国；
- World Partition 负责加载/卸载已保存地图格子，HLOD 保留望远镜所需的远处建筑轮廓；
- NPC 空间目录和 PCG 必须读取同一份固定 Visual World Layout；
- NPC 不得扫描当前 PCG Actor 来判断哪里有房屋、道路或工作地点；
- PCG 或地图格子卸载不能删除 ResidentID、HomeID、任务或空间映射；
- 首次要求作者操作 PCG、World Partition、HLOD 或 NavMesh 前，检查点必须给出逐步点击和验证说明。

## 10. 推荐的 Phase 7 分步和检查点

必须延续项目习惯：一次只实现一个检查点，给作者看大白话验收文档，作者确认后再提交并进入下一步。

### Phase 7-0：冻结 v2.0 可视化规则，不写功能代码

要做：

- 建立 `phase-7-visual-demo` 分支；
- 写 v2.0 可视化/互动演示规则；
- 更新当前权威规则索引；
- 明确正式/互动模式、Active 名额、空间规则、时间倍率、望远镜行为、记录与回放；
- 把仍需作者选择的问题列出来，不默认替作者决定。

检查点：作者能用大白话确认“画面里谁会出现、为什么出现、离开后保存什么、加速怎样运行、哪些数据不能用于论文正式统计”。

### Phase 7A：先做无画面的实时连接层

要做：

- 给统一会话增加最小的互动接口：提交想观察的 ResidentID 集合、释放居民、读取只读展示快照；
- 固定轨迹与互动选择互斥；
- 记录相机/望远镜观察命令并可回放；
- 整组 Active 替换要么全部成功，要么完全不改变旧状态；
- UI 永远拿不到可写账本、事件或 Cohort 内部对象。

检查点：无地图也能用一段固定镜头脚本反复得到相同 ResidentID、相同 Active 上限和相同领域结果；零时间切换不改身份、资源、房屋或任务。

### Phase 7B：先做无画面的空间与望远镜选择

要做：

- 建立确定性的街区、住宅点、工作区、道路和空间索引；
- 输入相机位置/朝向/望远镜目标，输出稳定的 Cohort 代理候选和最多 50 个 Active 请求；
- 实现优先级、名额、进入/退出距离、稳定排序、一个追踪目标和独立空间连续性；
- 记录候选访问数，禁止全人口逐帧扫描。

检查点：同一 Seed 和镜头轨迹选择相同居民；20k 到 100k 时，镜头查询不会接近 5 倍变重；快速扫镜头也不突破 50。

### Phase 7C：研究地图、俯视相机、鼠标移动和时间 UI

要做：

- 验证并固定 Dear ImGui 的 UE5.4 适配器，UI 只读取 Phase 7A 快照；
- 建立独立 World Partition 灰盒地图和导航；
- 作者按检查点步骤画少量道路/区域并放重要地标，PCG 在编辑器中生成和保存固定房屋/树木；
- 接入 World Partition 和 HLOD，不用运行时 PCG 重建王国；
- 实现相机跟随、自由移动、缩放和回到玩家；
- 实现鼠标点击地面移动玩家；
- 实现暂停、1x、2x、4x 和当前日期/时间显示；
- 先不追求美术质量，也不接复杂 NPC 动画。

检查点：玩家能在地图上点地移动；相机自由移动后不会被强制弹回；暂停时镜头/UI 可用；加速不会在单帧堆积大量小时步。

### Phase 7D：NPC Actor 池和动作表现

要做：

- 建立绑定真实 ResidentID 的远处 Cohort 轻量代理；
- 建立最多 50 个可复用完整 NPC Actor；
- 一对一绑定真实 Active ResidentID；
- 显示姓名、ID、职业、房屋状态、当前动作和任务剩余时间；
- 将 Work / ChopWood / BuyWood / Repair / Routine / Wait 映射到灰盒地点和基础动画；
- 先使用现有 Manny/Quinn 的站立、走路、跑步资源，缺失的砍柴、维修和望远镜动画可用占位表现。

检查点：Actor 回收不会删除居民；再次绑定同一居民时身份和任务连续；隐藏池对象不算逻辑人口；Actor 不回写资源和任务结果。

### Phase 7E：望远镜连续性演示

要做：

- 实现望远镜开关、瞄准区、持续观察阈值、远距 Streaming Source 和目标提示；
- 中心代理被持续观察后 Lift；望远镜目标和当前追踪居民拥有最高 Active 优先级；
- 地图/Actor 卸载后保留同一 ResidentID，玩家后来到达时重新绑定并找到同一个人；
- 展示前后姓名、房屋、动作、任务和剩余时间；
- 保存观察命令日志并支持重放。

检查点：同一脚本重复选择相同居民；居民不会凭空改名、换房或忘记维修；允许 Cohort 在离屏期间合理推进，不能要求画面冻结在离开前同一动画帧。

### Phase 7F：可视化总验收

要做：

- 完整编译和全部自动检查；
- 2k 用于快速开发验证，20k/100k 用于最终可选人口压力检查；
- 测量每个 `StepHour` 的中位数、P95、最大值，以及地震/政策小时；
- 测量 50 名 NPC 快速进出、相机快速扫动、望远镜反复开关、Actor 池和帧时间；
- 对比纯 UI 开关前后领域摘要；
- 输出大白话检查点和演示操作步骤。

检查点：画面目标完成、Active 不超过 50、纯表现不改变模拟、互动命令可回放、快速观察不全扫人口、关键场景没有明显卡顿或连续性穿帮。

## 11. Phase 7-0 已由作者确认的选择

1. 第一版只运行 Proposed v1.9 / StateImport；方法或场景切换必须重开运行；
2. 左键地面移动，左键 NPC 选择；WASD 自由移动相机，F1 回到玩家，自由相机不自动弹回；
3. 普通 Active 约 35、望远镜最多 5、切换/承诺/追踪缓冲约 10，总上限始终为 50；
4. 1x 初始为每真实秒推进 1 个游戏小时，2x/4x 成倍，每帧最多一个 StepHour；运行调试后可调整 Demo 配置；
5. 2k 用于快速开发，默认可视化 Demo 使用 20k，100k 仅为可选压力档；
6. Day -7 到 Day 0 在加载阶段预热，Day 60 显示结果并重开；
7. Dear ImGui 用作功能 UI，先暴露只读数据接口，再验证并固定 UE5.4 适配插件；
8. 固定 Visual World Layout 是 NPC 与 PCG 的共同空间来源；PCG 在编辑器中固定生成房屋/树木，World Partition/HLOD 负责运行时远近加载；
9. 允许少量绑定真实 ResidentID 的 Cohort 轻量代理；持续望远镜观察后才 Lift 为完整 Active Actor；
10. 第一版保留一个当前追踪居民，允许 Actor 卸载后保留身份、Active 名额和展示空间连续性；
11. 绝对观察距离、格子、HLOD、PCG 密度、代理预算和观察阈值在灰盒运行后作为 Demo 配置确定，不改变 v1.9。

## 12. 新会话最需要防止的错误

- 不要把 v1.9 改坏后直接覆盖原版本；
- 不要让正式固定激活轨迹和互动镜头同时运行；
- 不要让 UI、Blueprint、Actor、行为树或动画代码直接改金币、木材、房屋、任务或政策；
- 不要让 NPC Actor 自己再跑一套会决定研究行为的 AI；
- 不要每帧遍历 20k/100k 居民计算镜头距离；
- 不要生成 20k/100k 个隐藏 Actor 或 Character；
- 不要把镜头移动、望远镜开关或 Demo 运行写成正式实验数据；
- 不要为了加速一次性在同一帧推进很多小时；
- 不要在没有线程安全设计和测试前把现有模拟直接丢进后台线程；
- 不要一上来购买或制作大量美术资源。先用灰盒、现有模型和占位动画验证完整链路；
- 不要把“自动检查没有硬错误”说成“玩家一定看不出穿帮”；后者仍需要演示观察，若写论文强结论则需要用户研究。
