## 1. 这次用大白话解决了什么

H5 的问题是：远处社会知道“总共有多少房子坏了”，但不一定记得“具体是谁的房子坏了”。玩家靠近居民时，系统有时会把还在等维修的人恢复成房屋健康。

H6 没有让所有居民重新每小时各算一遍。它只为每栋房增加一个很小的状态记录：完好、等维修、维修中或已修好。远处仍按群体决定“这次修多少栋”，然后用固定顺序把这些名额对应到具体房屋。玩家靠近某个居民时，优先读取他自己的房屋记录；如果房屋正在维修，还会接回同一条批量维修任务的剩余时间。

## 2. 实际完成了哪些工作

- 每个 HomeID 有且只有一个紧凑房屋状态槽；
- 地震名单会同时更新群体总人数和名单中具体房屋；
- 一条批量维修事件继续代表整批人，但会保存它负责的房屋编号；
- 维修事件被拆成个人任务、再合回群体或最终完成时，房屋归属会一起移动；
- 玩家靠近或离开时，个人房屋状态必须和自己的 HomeID 对得上；
- 个人任务结束后，会同步更新他下一次应该回到哪个群体，避免“房已修好却回到损坏群体”；
- 增加住房人数、维修任务归属、玩家附近房屋状态和房屋内存的硬检查；
- 保留所有旧误差指标，并新增“维修承诺有没有丢”和“维修承诺还差多久”两把尺子；
- 摘要升级为 `1.9-domain-v1`，运行清单明确记录 v1.9 住房连续性模式。

每小时仍然不会扫描全部 Identity，也不会为一批维修生成逐居民事件、逐居民交易或逐居民思考。

## 3. Pilot 帮我们额外抓出的两个旧问题

第一次跑 5 Seed 时，检查门没有直接放行，而是抓出了两处以前不容易复现的问题：

1. 群体任务拆成个人后，个人真实账户里可能有 1 枚金币，但任务结束时又被旧群体平均值 0 覆盖；
2. 一名居民在玩家附近修好房屋后，虽然个人状态已是“修好”，他下一次离开玩家附近时仍可能回到旧的“房屋损坏”群体。

两处都已修正，并增加了三个专门检查：具体房屋恢复、三人分两枚金币、附近修好后再离开。临时定位日志已经删除。

## 6. 为什么仍然有 40 个住房差异

现在剩下的 40 个差异，不再是 Proposed 忘了这名居民自己的 HomeID。它们是 Oracle 和 Proposed 的维修排期本来就不同：

- Oracle 还在等维修，Proposed 已修好：8 个；
- Oracle 还在等维修，Proposed 已开始维修：12 个；
- Oracle 已修好，Proposed 还在等维修：12 个；
- Oracle 正在维修，Proposed 还在等维修：4 个；
- Oracle 正在维修，Proposed 已修好：4 个。

这 40 个观察点都伴随第一行动不同，所以它们是真实的近似误差，不能说成内部编号差异。但它们已经全部低于预先固定的 10% 复核线。

还有一个需要你明确知道的例子：Seed `20260813` 中，某居民在 Oracle 里还在等待、剩 1 小时；Proposed 已经进入维修、剩 25 小时。单个观察点相差 24 小时，因此该组“住房承诺剩余时间平均误差”为 6 小时。两边都记得居民正在处理住房问题，只是维修开始时机不同。v1.9 没有在看结果前为这个新增指标固定自动通过线，所以不能事后改标准，也不应该为了贴合这 5 个 Seed 继续调算法。

## 9. 现在能证明什么，不能证明什么

现在可以证明：Proposed 不会再仅因为居民离开玩家附近，就忘记他的具体房屋状态或正在进行的维修归属；这个能力的内存约每人 11 字节，也没有恢复每小时逐居民计算。

现在不能证明：Proposed 与 Oracle 会在同一小时修同一栋房，或每名居民的金钱、木材、行动时间完全一致。剩余差异正是论文要测量的“速度换取多少准确度”，不是必须消灭到 0 的程序错误。

这也不能替代正式 Shipping 环境、多轮统计实验或后续玩家可见演示。
