## 2. 实现时发现并修正了哪些问题

### 2.1 一个群体整批进入任务后，指定居民可能暂时找不到

例如 20 名工人一起工作 24 小时，这段时间原来的待命格子可能人数为 0。如果玩家此时靠近其中一人，只查待命格子就会错误地说“这个人不能恢复”。

现在只有在找不到待命格子时，系统才从这个居民所属群体正在执行的批量任务中确定性地拆出 1 人，并继承原任务的剩余时间和预订。原来 B4 已有待命格子时的选择规则不变，所以四个 B4 冻结 Digest 仍保持原值。

### 2.2 群体资源按平均数搬运会留下无人拥有的零头

例如 3 人共有 10 枚 Coin，如果简单按人均 3 枚创建整批事件，会有 1 枚 Coin 留在人数已经变成 0 的旧格子里。连续运行后，这些零头会影响行为和重建。

B5B 的完整运行路径改为按群体总账精确切分：前一批拿确定比例，最后一批拿走剩余总量。旧 B3/B4 隔离测试仍保持原模式和冻结 Digest，不会用改测试答案的方式掩盖变化。

### 2.3 分组标签必须和组内总资源对得上

复查每小时群体明细时发现过一个隐藏问题：某格子标记为“每人购买力 0—3”，里面有 17 人，但 Cash 与维修补助合计为 58。17 人在这一档最多只能有 51，所以人数和总账虽然都没丢，这个分组标签已经不可信；如果玩家刚好靠近这里，后续恢复具体居民时也可能无法给出符合该档位的个人状态。

现在每次资源变化后，系统都会用固定规则把群体重新放入符合实际资源区间的格子。它只按少量“资源档位”拆分，不会重新逐个扫描或生成全部居民。批量事件结束时如果要落入多个格子，事件日志也会诚实记录每个目标格子各有多少人、多少 Cash、维修补助和木材。

定向运行后独立检查了四个 Proposed 场景共 2,503 条可行动群体记录，购买力或木材与分组标签不一致的记录为 `0`。这项检查也已经加入每小时硬错误；以后再次出现就会让运行直接判定失败。

### 2.4 State Import 以前没有接入新版的到货和付款闭环

现在下单时先冻结国库付款并记录在途木材；三天后同一次操作把木材转入市场、完成付款并结束事件。任何一步失败，整次到货操作恢复到执行前状态。

## 3. 200 人 Oracle 对照实际结果

固定 Seed `20260810`、每个王国 100 人，运行了：

四个 Proposed Run 都没有人口、资源负数、重复付款、重复完成、事件归属、进入/退出或 Active 上限硬错误。最高 Active 为 20；每小时 Identity 扫描数为 0。

### 3.1 行为分布差多少

TVD 可以理解成“各种行为所占比例总体差了多少”，0 表示比例完全相同，越大表示差得越多：

| 场景 | Proposed 与 Oracle 的行为 TVD |
|---|---:|
| None | 0.001287 |
| HarvestCap | 0.000966 |
| StateImport | 0.001287 |
| RepairAid | 0.000432 |

这些值不是 0，说明新版确实是近似模型，不是把 Oracle 结果复制一遍；当前单 Seed 工程样本中的行为比例差异较小。

### 3.2 王国走势和政策效果差多少

每个场景中最大的归一化走势误差为：

- None：市场可用木材 `0.003331`；
- HarvestCap：市场可用木材 `0.003831`；
- StateImport：市场可用木材 `0.003331`；
- RepairAid：国库可用 Coin `0.005696`。

三个政策场景中最大的政策效果误差为：

- HarvestCap：木材价格 `0.000679`；
- StateImport：木材价格 `0.000055`；
- RepairAid：国库可用 Coin `0.005696`。

以上是既有指标按各自规模归一化后的工程数值，只能用于检查数据链已经接通，不能用单个 Seed 宣称统计结论。

### 3.3 玩家附近居民的连续性差多少

与 Oracle 的 60 个固定样本比较：

- 永久身份、房屋 ID、王国和职业不一致率都是 `0`；
- FirstAction 不一致率是 `0.05`，即 60 个样本中有 3 个第一次行动不同；
- Coin 不一致率约为 `0.6833–0.7000`，库存木材不一致率为 `0.05`，房屋状态不一致率为 `0.1333`；
- 原始 EventID 和剩余任务进度不一致率都是 `1.0`。

最后一项需要正确理解：Oracle 为每个人创建个人事件，新版为远处群体创建批量事件，因此两边的内部 EventID 本来就不应相同；批量行动的开始节奏也会让剩余进度不同。这不是人口或任务在进入/退出时丢失，因为新版自身的事件继承、拆分/合并和零时间往返硬检查全部为 0 错误。但它说明正式论文不能把“跨模型内部 EventID 必须相等”写成可见连续性的结论；正式实验前应把这项解释为表示差异，重点报告身份、可见状态、FirstAction 和新版自身的任务继承硬门。

## 7. 这些证据还不能证明什么

- 这只是一个固定 Seed 的工程检查，不是多 Seed 的 Pilot 或论文正式统计；
- 还没有证明 2k、10k、20k 的确定性、离线重建和生产性能；
- 还没有证明 50k、100k 能运行，或人口增加 5 倍时后台批量工作不会接近增加 5 倍；
- 还没有证明 20k Proposed 比 Per-Agent 至少快 3 倍；
- 跨模型 EventID 和剩余进度不能直接当作玩家可见连续性，需要在正式论文口径中解释清楚；
- 因此 B5 总验收仍未完成，`valid_for_formal_experiment` 必须继续保持 `false`。
