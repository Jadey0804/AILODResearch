## 4. 任务计时为什么看起来差得很大

总共 1200 个配对观察点中，有 1012 个是：

- Oracle 在观察的那个整点刚好没有剩余计时；
- Proposed 把居民从正在运行的群体 Routine 中恢复出来，显示还剩 8 小时；
- 双方当前目标都是 `RoutineLife`。

双方都显示 Routine 正在进行的 104 个观察点，剩余时间统一相差 7 小时。没有发现维修、买木、砍木或工作承诺造成这类计时差异。

大白话说：两边对“这个人此刻正在做日常背景活动，还是刚好站在两个日常活动之间”的记法不同。这会让旧的任务计时指标很难看，但目前证据没有显示重要维修承诺被忘掉。旧指标仍完整保留，不能因为解释得通就删除；后续可另加“重要承诺任务计时”，与 Routine 背景计时分开报告。

## 5. 住房状态里有一部分是真问题

1200 个观察点中，房屋状态逐字不同 204 个：

- 120 个是在 `Healthy` 和 `Repaired` 之间不同。两者通常都表现为房屋完好，主要差在历史标签；
- 84 个是玩家可能直接看出的状态不同，占全部观察点 7%。

这 84 个又刚好全部伴随激活后的第一件事不同：

- 76 个：Oracle 是 `DamagedWaiting + Wait`，Proposed 是 `Healthy + Routine`；
- 8 个：Oracle 是 `UnderRepair + ContinueRepair`，Proposed 是 `Healthy + Routine`。

五个 Seed 都出现了这种差异。Seed `20260812` 的四个场景均达到 `0.1167`，超过预先固定的 0.10 FirstAction 复核线；Seed `20260814` 为 0.10，其他 Seed 较低。

大白话说：社会总量和修好多少房子没有丢，但群体解聚时不一定把“哪一栋具体房子仍坏着”还给与 Oracle 相同的居民。因此玩家靠近某个人时，可能看到 Oracle 认为他在等修房，Proposed 却把他恢复成房屋健康并去做日常活动。这是受控近似的真实误差，不应伪装成纯内部编号差异。

## 7. 当前结论

加固工具本身已经完成：误差能说明“差多少”，实验能固定乱序和续跑，内存能分项，完整回归也通过。

但 v1.7 的正式模型资格暂不打开。原因不是系统会崩、资源不守恒或性能不够，而是住房状态与第一行动的近似误差已经重复出现，并且有一个 Seed 超过预先固定的复核线。H0 规定越线后必须先读明细并由项目作者决定，不能由实现者自行改标准或调模型。

## 8. 我推荐的下一步

我推荐新增一个很短的 v1.9 / H6“住房连续性定向修正”，不推翻 Cohort Batch：

1. 为每个 HomeID 保存非常紧凑的当前房屋状态，或保存能重建该状态的等价紧凑记录；
2. 批量维修仍按群体计算人数、资源和事件，不恢复逐 NPC 每小时思考；
3. 当批量房屋状态变化时，用固定规则更新具体 HomeID；
4. Lift 某居民时，房屋状态优先读取其 HomeID 的记录，避免把仍在等修或正在维修的人恢复成 Healthy；
5. 保留当前所有旧误差指标，并另加“重要承诺任务计时”，把 Repair 等玩家关心的承诺与 Routine 背景计时分开；
6. 重新跑本次 5 Seed Pilot、20k 速度门和 100k Proposed 内存/压力检查。

这会增加少量随人口增长的紧凑房屋状态内存，但不应重新引入每小时 O(N) 扫描、每人候选、每人事件或每人账本。正式设计前仍需估算每人占多少字节，以及批量维修怎样选择 HomeID，避免借“连续性”之名退回 Per-Agent。

另一个可选方向是接受当前近似，并在论文中明确报告：玩家可见住房/首行动差异约 7%，单个 Seed 最高约 11.7%。这个选择更省工，但对于“玩家附近恢复成可信 NPC”的目标，我不推荐直接接受。
